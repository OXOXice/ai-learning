# 02 · 六种常用模式

都是"能显著改变结果"的技巧，不是玄学。每种都给出适用场景和失效场景。

## 1. Few-shot（给例子）

```
把下面的用户反馈分类为：功能 / 性能 / 界面 / 其他。

示例1：输入"点了没反应" → 功能
示例2：输入"加载太慢了" → 性能
示例3：输入"按钮颜色太丑" → 界面

输入："导出的时候卡死"
```

- **适用**：分类、风格模仿、格式对齐、边界模糊的任务
- **失效**：例子太少（<2）或例子互相矛盾；例子里的偏见会被照抄
- **技巧**：例子要覆盖**边界情况**（模棱两可的那几个），不要只放典型样本

## 2. CoT（思维链）

```
先列出解题步骤，再给最终答案。步骤用 1. 2. 3. 编号。
```

- **适用**：数学、逻辑、多条件判断、代码调试
- **失效**：简单任务反而变慢变啰嗦；步骤写错会把答案带偏
- **进阶**：要求"每步写出依据"，比只写步骤更抗幻觉

## 3. 任务分解（Decomposition）

一个大任务拆成串行小任务，每步单独调用：

```
原文 → ① 提取关键事实 → ② 按重要性排序 → ③ 写成 3 句话摘要
```

- **适用**：长文摘要、数据抽取、复杂报告
- **好处**：每步可验证、可缓存、失败可重试
- **代价**：多次调用更贵；步骤间信息会损失

## 4. 自我检查（Self-check / Reflexion）

```
第一步：给出答案。
第二步：检查这个答案，列出至少 2 个可能的错误或反例。
第三步：如果发现错误，输出修正后的答案；如果没有，说明为什么没问题。
```

- **适用**：事实性回答、代码、需要严谨的结论
- **注意**：让同一个模型"自己检查自己"，抓得住低级错误，抓不住系统性误解
- **更强的做法**：换一个模型/另一个角色来审（"审稿人"人设）

## 5. 角色与视角（Persona）

```
你是 10 年经验的数据库 DBA，正在评审一个新手写的 SQL。
```

- **适用**：需要特定专业视角、需要跳出默认的"老好人"语气
- **失效**：角色和任务不匹配时，只是换了个口吻；角色不能凭空增加知识

## 6. 格式约束

```
输出严格的 JSON，字段：{"title": str, "tags": [str], "score": 0-10}
不要输出任何 JSON 之外的内容。
```

- **适用**：要接程序、要批量处理
- **必须配合**：代码侧解析失败重试 + schema 校验（见 [03 篇](03-结构化输出与工具调用.md)）

## 组合用法

真实场景几乎都是组合的。例如"把会议记录变成行动项"：

> 角色（项目经理）+ 示例（2 条）+ 分解（先抽决议，再抽负责人，再排期）+ 格式（JSON 数组）
