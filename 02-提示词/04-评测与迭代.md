# 04 · 评测与迭代

## 一句话总结

**没有测试集的提示词优化 = 玄学**。建 20 条覆盖典型的输入，每次改完都重跑一遍，只看分数，不看感觉。

## 1. 最小的评测闭环（半天能搭完）

```
cases.jsonl      ← 20 条输入 + 期望特征
prompt_v1.md     ← 提示词版本
run_eval.py      ← 逐条跑，打分，输出报告
results/         ← 每次跑的结果存一份，可对比
```

`cases.jsonl` 一行一条：

```json
{"id": 7, "input": "导出的时候卡死", "expect_label": "性能", "note": "边界：功能还是性能"}
```

## 2. 打分方式（从便宜到贵）

| 方式 | 成本 | 适合 |
|---|---|---|
| 精确匹配 / 关键词命中 | 免费 | 分类、抽取 |
| 代码校验（能跑吗、JSON 合法吗） | 免费 | 代码、结构化输出 |
| LLM 当裁判（给评分标准让它打分） | 低 | 开放式生成 |
| 人工打分 | 高 | 最终验收、抽样校准 |

**LLM 裁判的写法**要具体：

```text
按以下标准给回答打分 1–5：
5 = 结论正确且给出依据
3 = 结论正确但依据缺失
1 = 结论错误
只输出数字。
```

## 3. 迭代纪律

1. 一次只改一个变量（改措辞就别同时改模型）
2. 每次跑全量 20 条，记录通过率
3. 新的失败案例**追加**进 cases，不要临时改期望去凑通过率
4. 通过率提升 10% 以上才值得保留这次改动

## 4. 常见假象

| 假象 | 真相 |
|---|---|
| "我试了 3 次都对" | 样本太少，可能只是运气 |
| "新提示词明显更好" | 没有对照，可能模型自己就不稳定 |
| "通过率 95% 了" | 检查 cases 是不是太简单，加边界案例 |
| "换个模型就都好了" | 换模型等于重开，评测集要重跑 |

## 5. 记录表（贴进你的提示词库）

| 版本 | 改动 | 通过率 | 花的时间 | 结论 |
|---|---|---|---|---|
| v1 | 初版 | 13/20 | — | 基线 |
| v2 | 加 2 个 few-shot | 17/20 | 20min | 保留 |
| v3 | 加"不要解释" | 16/20 | 10min | 回退 |

## 动手实验

给你第 3 周写的 10 条提示词里最常用的那一条，建 20 条 cases，跑一次基线，然后只改一处措辞，再跑。把这张表填出来。
