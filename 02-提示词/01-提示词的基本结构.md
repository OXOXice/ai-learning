# 01 · 基本结构

## 六个槽位

```
[1 角色]     你是谁 / 站在什么立场
[2 任务]     一句话说清要产出什么
[3 上下文]   必要背景、资料、约束条件
[4 规则]     必须做 / 绝对不要做
[5 输出格式] 结构、长度、语言、示例
[6 示例]     1–2 个输入输出对照（可选但极其有用）
```

不是每次都要六段全写，但**缺哪个槽位，就对应哪里出问题**：

| 缺 | 症状 |
|---|---|
| 任务 | 答非所问、洋洋洒洒 |
| 上下文 | 泛泛而谈、用通用知识瞎猜 |
| 规则 | 跑题、加戏、瞎编 |
| 输出格式 | 每次格式都不一样，没法程序处理 |
| 示例 | 风格不稳、边界模糊 |

## 一个"合格"的例子

```text
你是资深代码审查员，只关注会导致线上事故的问题，不评价风格。

任务：审查下面的 Python 函数，找出会导致崩溃或数据错误的缺陷。

上下文：
- 这段代码每天处理约 100 万条订单
- 数据源偶尔会返回 null
- 下游依赖 amount 必须是正数

规则：
- 只报 3 条以内，按严重程度排序
- 每条给出：问题、触发条件、修复代码
- 没问题就说"未发现严重缺陷"，不要凑数

输出格式：
1. [严重程度] 问题：… / 触发条件：… / 修复：```python ...```
```

对比一下常见的坏版本：

```text
帮我看看这段代码有什么问题，写详细一点
```

后者的输出大概会是十条"建议加类型注解""建议加注释"——不是错，但没用。

## 三个结构性技巧

1. **用分隔符隔离资料**：`<document>…</document>` 或 `###`，避免资料里的文字被当成指令（提示注入的主要入口）
2. **把最重要的约束放最后**：模型对结尾更敏感；长提示里，把"绝对不要"放在结尾比开头管用
3. **正面表述优先**：`只输出 JSON` 比 `不要输出解释` 更有效，因为前者给了明确目标

## 动手实验

把上面那段"代码审查"提示词应用到一段故意有 bug 的代码，然后用 [04 篇](04-评测与迭代.md) 的方法做 5 条测试，删掉"规则"这一段再跑一遍，比较输出差异。
