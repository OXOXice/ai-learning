# 06 · 推理参数与成本

## 一句话总结

温度管"多随机"，top_p 管"从多小的候选池里抽"，max_tokens 管"最多说多长"，上下文管"能记多少"——这四个旋钮直接决定输出的稳定性和你的账单。

## 核心概念

### 1. 采样旋钮

| 参数 | 作用 | 典型值 | 什么时候调 |
|---|---|---|---|
| `temperature` | 把概率分布"压平"或"尖锐化"。0 = 永远取最大概率 | 事实问答 0–0.3；创意 0.8–1.0 | 输出跑偏就降，输出死板就升 |
| `top_p` | 只在累计概率前 p 的候选里抽（核采样） | 0.9–0.95 | 通常和温度二选一调，别同时大幅动 |
| `top_k` | 只在前 k 个候选里抽 | 20–50 | 需要硬限制候选时 |
| `max_tokens` | 硬上限，超了直接截断 | 按任务给 | 防跑飞、控成本 |
| `stop` | 遇到指定字符串就停 | 如 `"\n\n"` | 结构化输出时很有用 |
| `seed` | 固定随机种子（部分服务支持） | 任意 | 做评测对比时需要可复现 |

**重要**：`temperature=0` 也不是绝对确定——并行计算和浮点误差会让结果偶有差异。要复现，需固定 seed 并接受近似。

### 2. 提示词工程里最常被忽略的旋钮：上下文

给你的每一个 token 都算钱，而且**每轮对话都要把历史重新发一遍**。所以：

- 10 轮的对话，第 10 轮的成本 ≈ 前 9 轮全部内容
- 解决：摘要压缩历史、只保留最近 N 轮、把不动的资料放前面吃缓存

### 3. 成本与延迟

```
单次成本 ≈ (输入 token 数 × 输入单价) + (输出 token 数 × 输出单价)
```

通常输出比输入贵 2–4 倍。所以：
- 让模型"少废话"是省钱手段：`只输出结果，不要解释`
- Agent 循环是成本黑洞：每轮都要重发全部历史 + 工具结果

### 4. 缓存（prompt caching）

很多服务对"开头完全相同的长 prompt"打折。做法：把系统提示词、长文档放在**最前面且保持不变**，把变化的部分放最后。能省 50%–90%。

### 5. 结构化输出

要求 JSON 时要注意：
- 明确写 schema，给一个示例
- 加 `不要输出多余文字`
- 代码里必须做**解析失败重试**，不要假设一定合法
- 更稳的做法是用工具调用 / JSON mode（服务端约束解码）

## 动手实验

### 实验 1：温度扫描

同一个创意任务（写 3 条广告语），用 `temperature` = 0、0.7、1.2 各跑 3 次，记录：
- 每次输出是否相同
- 质量评分（1–5，自己打）
- 有没有出现离谱内容

画一张表，得出**你自己任务**的最佳温度。

### 实验 2：成本测量

写一个函数，跑完打印 `prompt_tokens / completion_tokens / 估算费用`。拿它跑：
- 短问题（20 字）
- 长问题（2000 字文档 + 提问）
- 10 轮连续对话

比较数量级差多少。

### 实验 3：缓存生效吗

用同一段 3000 字文档，连续问 5 个问题（文档位置不变）。观察第 2 次起 `prompt_tokens` 的计费是否打折（形如 `prompt_cache_hit_tokens` 字段）。
